SNJPro · application web de gestion

Comprendre (et pouvoir refaire) le frontend SNJPro

Ce guide explique tout le projet Angular : à quoi sert chaque dossier et chaque fichier de configuration, comment l'application démarre, comment elle parle au backend Spring Boot, comment l'authentification JWT est gérée côté navigateur, comment sont construits les écrans, le système de design et les thèmes clair / sombre. Après lecture, on doit pouvoir le maintenir… ou le refaire.

En une phrase

SNJPro WebUne application monopage (SPA) Angular 21 en composants autonomes et signaux, qui affiche les écrans de gestion du Service National des Jeunes (membres, cohortes, mobilisations, présences…) et consomme l'API REST du backend (http://localhost:8080/api) avec un jeton JWT.

Ce que gère l'application

👥 Membres & cohortes

Comment le front et le back se répartissent le travail

NavigateurAngular (ce projet)
Affiche les écrans, valide les saisies pour le confort, garde le jeton, masque ce que l'utilisateur ne peut pas faire.
⇅ HTTP + JSON · en-tête Authorization: Bearer <jwt>
API RESTSpring Boot (snjpro_back)
Seule source de vérité : vérifie le jeton, les rôles et le périmètre, applique les règles métier, lit/écrit MySQL.
Règle d'orTout ce que fait le front pour la sécurité (gardes de route, menus masqués, boutons cachés) n'est que du confort. Le backend revérifie chaque appel (@PreAuthorize, périmètre) : un utilisateur qui forge une requête obtient un 403.

Chapitre 3

Architecture

Le code est rangé par responsabilité. Une page ne fait jamais d'appel HTTP elle-même : elle passe par un service.

pages/écrans
Un composant par écran (liste, formulaire, détail). Il lit des signaux, appelle les services, affiche. Chargé à la demande par le routeur.
▼ appelle
core/services/services métier
Un service par domaine (MembreService, ActiviteService…) : une méthode = un endpoint du backend. Injecte HttpClient et renvoie des Observable typés avec les modèles générés.
▼ HttpClient
environmentssrc/environments
Chaque service construit son URL depuis environments.apiUrl ; shared/utils/http.ts fournit toParams, formulaire (multipart), enregistrerFichier (téléchargements) et urlLocale (images protégées).
▼ intercepteurs
sessionInterceptor · erreurInterceptorcore/interceptors
sessionInterceptor ajoute Authorization: Bearer … ; erreurInterceptor intercepte les 401 (session expirée ⇒ retour à la connexion).
▼ réseau
Backendlocalhost:8080/api
Spring Boot (voir le guide du backend).

Les autres familles

layout/

La « coquille » commune : barre latérale, barre du haut, recherche Ctrl K, panneau de notifications, mise en page des écrans de connexion. Les pages s'affichent dans son <router-outlet>.

shared/

Briques réutilisées partout : icônes, avatar, modale, graphiques, pagination, pastilles, QR code, toasts, popups de sélection, pipes de format, libellés.

models/

api.models.ts : les interfaces TypeScript générées depuis les DTO Java du backend. Le front et le back partagent ainsi les mêmes formes de données.

Qui garde l'état ?Pas de « store » global : l'état partagé vit dans des services providedIn: 'root' à base de signaux — AuthService (utilisateur, permissions), ShellService (compteurs du menu, menu replié, panneaux ouverts), ThemeService (thème), ToastService, ConfirmationService. L'état d'un écran reste dans son composant.

Chapitre 6

Démarrage de l'application & SSR

Du chargement de la page au premier écran, pas à pas.

app.config.ts : les « fournisseurs » globaux

ts
export const appConfig: ApplicationConfig = {
  providers: [
    provideBrowserGlobalErrorListeners(),                 // erreurs non interceptées → console
    provideRouter(routes,
      withComponentInputBinding(),                        // :id de l'URL → input id() du composant
      withInMemoryScrolling({ scrollPositionRestoration: 'top' })),
    provideHttpClient(withFetch(),                        // HttpClient basé sur fetch()
      withInterceptors([erreurInterceptor, sessionInterceptor])), // 401 + jeton JWT
    { provide: LOCALE_ID, useValue: 'fr-FR' }             // dates et nombres en français
  ]
};
Pourquoi un serveur SSR si le rendu est côté client ?Le projet a été créé avec ng new --ssr. app.routes.server.ts déclare RenderMode.Client pour toutes les routes : le serveur Express (server.ts) ne fait que servir les fichiers et la coquille HTML. Le rendu serveur n'apporterait rien (pas de référencement à soigner, pages réservées aux connectés, jeton stocké dans le navigateur). Conséquence pour le code : tout accès à localStorage, window ou document est protégé par isPlatformBrowser(PLATFORM_ID) ou placé dans afterNextRender.

Chapitre 8

Signaux & détection de changement

Comment l'écran se met à jour quand une donnée change.

signal()

Une valeur observable : on la lit en l'appelant (membres()), on la change avec .set() ou .update(). Angular sait quels templates l'ont lue et ne redessine qu'eux.

computed()

Une valeur dérivée, recalculée seulement quand un signal lu change. Ex. connecte = computed(() => !!this.utilisateur()?.token).

effect()

Un effet de bord qui se relance quand ses signaux changent. Ex. ThemeService pose data-theme sur <html> à chaque changement de thème.

ts
// Extrait simplifié de pages/activites/activites.ts
protected readonly selection = signal<ActiviteDTOs.Resume | null>(null);
protected readonly c = computed(() => this.selection()?.compteurs ?? null);

protected choisir(a: ActiviteDTOs.Resume) {
  this.selection.set(a);            // → le template qui lit selection() / c() est redessiné
}
Zoneless + OnPushLe projet n'inclut pas zone.js. Les composants sont en ChangeDetectionStrategy.OnPush (56 sur 57) : ils ne sont revérifiés que lorsqu'un signal qu'ils lisent change, qu'un événement du template se produit ou qu'une entrée change. C'est pourquoi l'état d'écran est presque toujours un signal : une simple propriété modifiée dans un subscribe ne serait pas forcément réaffichée.
Propriétés « classiques » liées par ngModelLes objets de formulaire (nouvelle, f, filtre…) restent des propriétés simples modifiées par [(ngModel)] : l'événement de saisie déclenche lui-même le rafraîchissement du composant.

Abonnements et nettoyage

  • Appels HTTP : subscribe() direct, ils se terminent seuls après la réponse.
  • Flux longs (événements du routeur, recherche avec debounceTime) : .pipe(takeUntilDestroyed()), désabonnement automatique à la destruction du composant.
  • Minuteries (setInterval du rafraîchissement des présences, compte à rebours du QR) : arrêtées dans ngOnDestroy.
  • toSignal() transforme un Observable en signal (URL courante dans la barre latérale).
Chapitre 9

Templates & formulaires

Contrôle de flux intégré

@if (cond) { … } @else { … }, @for (x of liste(); track x.id) { … } @empty { … }, @switch. Remplacent *ngIf/*ngFor (plus rapides, pas d'import). track est obligatoire : il permet de ne recréer que les lignes qui changent.

Liaisons

{{ valeur }} interpolation · [prop]="expr" propriété · (evt)="méthode($event)" événement · [class.active], [style.width.%] classes et styles · [attr.aria-label] attribut.

Formulaires « template-driven »

FormsModule + [(ngModel)] (224 usages). Choix assumé : formulaires simples, validation légère côté front, la vraie validation est faite par le backend (@Valid) et ses messages sont affichés via messageErreur().

Pipes

Transforment une valeur à l'affichage : {{ n | nombre }} → « 1 284 », | dateCourte, | dateHeure, | heure, | relatif (« il y a 5 min »), | taille (« 2,4 Mo »), | telMasque.

Templates en ligne ou fichiers séparés ?Les petits composants ont template et styles dans le .ts ; les gros écrans ont templateUrl (.html) et styleUrl (.css). Les styles d'un composant sont encapsulés : ils ne débordent pas sur le reste de l'application (sauf ::ng-deep, utilisé 5 fois pour styler un composant enfant).
Chapitre 10

Routage & lazy loading

app.routes.ts définit toutes les routes, regroupées par sections commentées : les écrans publics (dans AuthLayout), l'espace de gestion (dans MainLayout, protégé par authGuard) et deux écrans isolés (accès refusé, projection plein écran).

ts
{ path: '', component: MainLayout, canActivate: [authGuard], children: [
  { path: 'activites', title: 'Activités & présences · SNJPro',
    loadComponent: () => import('./pages/activites/activites').then(m => m.Activites) },
  { path: 'membres/nouveau', title: 'Nouveau membre · SNJPro',
    canActivate: [roleGuard], data: { roles: GESTION_MEMBRES },
    loadComponent: () => import('./pages/membres/nouveau/nouveau-membre').then(m => m.NouveauMembre) },
  …
]}
  • loadComponent : le code d'un écran n'est téléchargé que lorsqu'on y va (un « chunk » JavaScript par page). Le premier chargement reste léger.
  • title : titre de l'onglet du navigateur.
  • withComponentInputBinding() : les paramètres d'URL (/membres/:id) et de requête arrivent directement dans les input() du composant.
  • Ordre : la redirection '' → tableau-de-bord est placée avant le bloc public, sinon celui-ci capterait « / ». La route ** renvoie au tableau de bord.

Chapitre 11

Authentification côté navigateur (JWT)

Le backend est sans session (stateless) : il délivre un jeton JWT que le front garde et renvoie à chaque appel.

Où est stocké le jeton ?

« Rester connecté »StockageDurée
cochélocalStorage['snjpro.session']Survit à la fermeture du navigateur, jusqu'à l'expiration du jeton (24 h côté backend) ou la déconnexion.
décochésessionStorage['snjpro.session']Effacé à la fermeture de l'onglet.

La valeur stockée est la réponse complète de /auth/login (AuthResponse : jeton, rôle, nom, région, photo…). Au démarrage, AuthService.lireSession() la relit pour que l'utilisateur reste connecté après un rechargement.

Sécurité du stockageUn jeton en localStorage est lisible par tout script de la page : la protection repose sur l'absence de faille XSS (Angular échappe automatiquement les interpolations ; bypassSecurityTrustHtml n'est utilisé que pour les icônes, dont le contenu est fixe). Alternative plus robuste : cookie HttpOnly posé par le backend.

Anatomie de l'intercepteur

ts
// core/interceptors/session.interceptor.ts
export const sessionInterceptor: HttpInterceptorFn = (req, next) => {
  const token = inject(AuthService).token;
  if (!token || !req.url.startsWith(environments.apiUrl)) return next(req); // jeton seulement vers NOTRE API
  return next(req.clone({ setHeaders: { Authorization: `Bearer ${token}` } })); // requêtes immuables → clone
};

// core/interceptors/erreur.interceptor.ts
export const erreurInterceptor: HttpInterceptorFn = (req, next) => {
  const auth = inject(AuthService), router = inject(Router);
  return next(req).pipe(catchError(erreur => {
    if (erreur.status === 401 && !routePublique(req) && auth.connecte()) {
      auth.effacer();                                       // jeton expiré ou révoqué
      router.navigate(['/connexion'], { queryParams: { expire: 1 } });
    }
    return throwError(() => erreur);                     // l'écran affiche quand même son erreur
  }));
};
Pourquoi exclure les routes publiques du 401 ?Sur /auth/login, un 401 veut dire « identifiant ou mot de passe incorrect », pas « session expirée » : il ne faut ni effacer la session ni rediriger.
Chapitre 12

Gardes de route & permissions

authGuard

Espace de gestion. Non connecté ⇒ /connexion?retour=…. Rôle MEMBRE ⇒ /acces-refuse (les membres utilisent l'application mobile).

invitesGuard

Écran de connexion : si l'on est déjà connecté, on est envoyé au tableau de bord.

roleGuard

Lit les rôles autorisés dans data: { roles: [...] } de la route et restreint l'accès à cette liste (création d'un membre, rédaction d'actualités, gestion des mobilisations et des opportunités).

Trois niveaux de filtrage

  1. Menu — la barre latérale n'affiche une entrée que si auth.peutVoir(module) : matrice des permissions du rôle lue sur GET /api/auth/permissions (modifiable dans Utilisateurs & rôles).
  2. Route — les gardes ci-dessus.
  3. Boutons — dans les écrans, auth.aRole(…) ou un computed (peutGerer) masque les actions (créer, modifier, supprimer).

Chapitre 13

Communication avec l'API

Chaque service injecte HttpClient et construit ses URL depuis environments.apiUrl (src/environments/environments.development.ts pour ng serve, environments.ts pour ng build). Les petites fonctions communes sont dans shared/utils/http.ts.

FonctionUsage
toParams({ … })Paramètres de requête : null/undefined/vides ignorés ; un tableau devient un paramètre répété (?region=Kayes&region=Ségou).
formulaire({ fichier, … })Corps multipart/form-data (photo, document, fichier d'import). Avec { reportProgress: true, observe: 'events' } : barre « 72 % ».
map(urlLocale)Image ou PDF protégé : téléchargé avec le jeton (responseType: 'blob') puis transformé en URL locale blob: affichable dans <img> (une balise <img src> classique n'enverrait pas l'en-tête Authorization).
tap(enregistrerFichier)Export Excel/CSV/PDF (observe: 'response') : lit le nom dans Content-Disposition et déclenche l'enregistrement du fichier.

Un service métier type

ts
@Injectable({ providedIn: 'root' })
export class ActiviteService {
  private readonly http = inject(HttpClient);
  private readonly apiUrl = `${environments.apiUrl}/activites`;

  lister(statut?: StatutActivite | null, annee?: number, mois?: number): Observable<ActiviteDTOs.Resume[]> {
    return this.http.get<ActiviteDTOs.Resume[]>(this.apiUrl, { params: toParams({ statut, annee, mois }) });
  }

  saisir(id: number, s: ActiviteDTOs.SaisieManuelle): Observable<ActiviteDTOs.PresenceDTO> {
    return this.http.post<ActiviteDTOs.PresenceDTO>(`${this.apiUrl}/${id}/presences`, s);
  }

  exporter(id: number, format: FormatFichier = 'XLSX'): Observable<HttpResponse<Blob>> {
    return this.http.get(`${this.apiUrl}/${id}/presences/export`, { params: toParams({ format }), responseType: 'blob', observe: 'response' })
      .pipe(tap(enregistrerFichier));
  }
}

Gestion des erreurs

messageErreur(err) (dans shared/utils/http.ts) transforme toute erreur HTTP en phrase lisible, affichée par ToastService :

CasMessage affiché
status 0« Impossible de joindre le serveur SNJPro. Vérifiez que le backend est démarré. »
Erreur de validation (errors: {champ: message})Les messages des champs, séparés par « · »
Corps avec message (règle métier, 409…)Le message du backend
403 / 404« Vous n'avez pas les droits pour cette action. » / « Élément introuvable. »
Recette d'un écran1) le composant appelle service.methode().subscribe({ next, error }) ; 2) next met à jour un signal (le template se redessine) et affiche un toast de succès ; 3) error affiche toast.error(messageErreur(e)). Un signal envoi désactive le bouton pendant l'appel pour éviter les doubles clics.
Chapitre 14

Modèles générés depuis le backend

src/app/models/api.models.ts n'est pas écrit à la main : il est produit par scripts/generer-modeles.js à partir des DTO et énumérations Java.

Ce que fait le générateur

  • lit dto/*.java et enumeration/*.java du backend ;
  • une classe DTO → une interface (champs optionnels ?) ;
  • une classe « …DTOs » regroupant des classes static → un namespace (ActiviteDTOs.Resume) ;
  • un enum Java → un type union ('EN_COURS' | 'TERMINEE' | …) ;
  • types : String/LocalDate/LocalDateTime → string, nombres → number, List<X> → X[], Map → Record.

Quand le relancer ?

Après toute modification d'un DTO ou d'une énumération côté backend :

bash
SNJ_BACK=/home/mohamed/Documents/projet_spring_boot/snjpro_back npm run modeles

Sans SNJ_BACK, le script cherche le backend dans ../snj_pro_backend à côté du projet. Vérifier ensuite avec git diff que seuls les champs attendus ont changé, puis ng build : les écrans qui utilisaient un champ supprimé ne compilent plus (c'est voulu).

Ne jamais éditer api.models.ts à la mainLa modification serait écrasée à la prochaine génération. Les types propres au front (ex. DeuxiemeFacteur, PreferenceTheme) sont déclarés dans les services.

Chapitre 18

Listes déroulantes & calendriers stylés

Les popups natives de <select> et <input type="date|month|datetime-local|time"> sont dessinées par le système : le CSS ne les atteint pas. Selecteurs les remplace pour toute l'application, sans toucher aux templates.

À savoir pour écrire un écranRien à faire : un <select class="select" [(ngModel)]="…"> ou un <input type="date" class="input"> classique reçoit automatiquement le panneau stylé, le clavier (flèches, Entrée, Échap, saisie de lettres) et respecte min, max, required, disabled. Les listes multiples (multiple, size>1) et les <datalist> restent natives.
Chapitre 19

Écrans & modules

Chaque écran, son composant, les services qu'il utilise et les endpoints du backend. Filtrez la liste.

Zoom : Souvenirs de formation

Écran /souvenirs (pages/souvenirs/) : photos, vidéos et sons de la formation, par cohorte. Entrée « Souvenirs » du groupe Communication (module SOUVENIRS), avec un badge du nombre d'envois de membres à valider (ShellService → /souvenirs/statistiques).

  • Galerie : compteurs (publiés, à valider, photos, vidéos, sons), onglets Publiés / À valider / Rejetés (masqués pour la direction, qui ne voit que les publiés), filtre par type, cohorte et recherche, cartes avec la première photo en couverture, pagination par 12.
  • Visionneuse (app-modal 1020 px) : <img>, <video controls> ou <audio controls>, flèches et miniatures, ajout / retrait de fichiers, et selon le statut : Publier, Rejeter (motif obligatoire, montré au membre), Modifier, Supprimer.
  • Ajout : titre, légende, cohorte (limitée au périmètre : sa cohorte pour un responsable de cohorte, les cohortes de sa région pour un responsable régional), date de prise de vue, lieu, « visible par tous les membres », zone de dépôt multi-fichiers avec aperçus ; contrôle côté navigateur (10 fichiers, 100 Mo, formats) puis envoi multipart avec barre de progression (uploadSuivi).
  • Fichiers protégés : chaque média est récupéré avec le jeton puis affiché via une URL blob: (SouvenirService.fichier : responseType: 'blob' puis map(urlLocale)), mise en cache par identifiant et libérée (URL.revokeObjectURL) à la sortie de l'écran.
  • Envois multiples : formulaire() (shared/utils/http.ts) accepte une liste de fichiers sous un même nom de champ (ChampsFormulaire).
  • Une alerte « Nouveau souvenir à valider » de la cloche ouvre directement le souvenir (/souvenirs?id=…).

Zoom : Activités & présences (US14)

« En tant que responsable, je veux enregistrer la présence des membres lors d'une activité afin de conserver une trace de leur participation. » — écran /activites (pages/activites/).

Critère d'acceptationDans l'interface
Un QR code peut être associé à l'activité« Nouvelle activité » : interrupteur Générer un QR code de présence. Le QR (app-qr-code) et son code à 6 caractères s'affichent dans la fiche, rafraîchis toutes les 15 s ; bouton Plein écran → /activites/:id/projection (QR géant renouvelé toutes les 30 s, compteur, dernières arrivées en direct) à afficher sur un écran à l'entrée. « Terminer » désactive le QR.
Le membre peut être identifiéLe membre scanne le QR dans l'application mobile (son compte l'identifie). Sans téléphone : Saisir une présence → recherche par nom, prénom ou identifiant SNJ (MembreService.rechercher, avec debounceTime), heure d'arrivée et motif.
La présence est enregistréePOST /activites/{id}/presences ; les compteurs (présents / inscrits, taux, arrivées de la dernière heure, saisies manuelles) se mettent à jour. Un doublon renvoie le message du backend (409).
Un responsable peut consulter les présencesTableau des derniers pointages dans la fiche, et bouton Voir toutes les présences (N) : registre complet paginé (membre, identifiant, date et heure, mode QR / code / manuel, motif, saisi par), retrait d'un pointage erroné, export Excel.
Gestion de l'activitéLe crayon ouvre « Modifier l'activité » (même formulaire que la création, description comprise) ; la corbeille n'apparaît que s'il n'y a encore aucune présence (sinon le backend refuse : on termine l'activité). Les actions sont réservées à peutGerer() : administrateurs, agents SNJ, responsables régionaux et de cohorte.

Chapitre 22

Points d'attention & améliorations

Adresse de l'API en durAPI_URL vaut http://localhost:8080/api. → passer par une variable de build (fileReplacements / define) ou un fichier de configuration chargé au démarrage pour la production.
Jeton dans le stockage du navigateurLisible par JavaScript : la moindre faille XSS l'exposerait. → cookie HttpOnly + SameSite côté backend à terme.
Pas de « refresh token »À l'expiration (24 h), l'utilisateur est renvoyé à la connexion au premier 401.
TestsUn seul test (création du composant racine). → tester au moins les services (avec HttpTestingController), les gardes et les écrans critiques (connexion, création de membre, présences).
ResponsiveLes écrans suivent les maquettes 1280 px ; quelques règles adaptent les grilles sous 1100 et 720 px, mais la barre latérale n'a pas encore de mode « tiroir » mobile.
AccessibilitéLibellés aria-label sur les boutons-icônes, navigation clavier dans les popups de sélection ; à compléter par un audit (contrastes en mode sombre, ordre de tabulation des modales).
SSR inutiliséLe serveur Express n'apporte rien en RenderMode.Client : l'application pourrait être servie comme simples fichiers statiques (Nginx).
InternationalisationTextes en français écrits dans les templates. Pour une autre langue : @angular/localize (i18n).
